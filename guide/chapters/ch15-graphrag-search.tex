\chapter{GraphRAG \& Search}
\label{ch:graphrag-search}

When a user asks ``Why did I choose PostgreSQL over MongoDB?'',
\sysname{} must find the relevant decisions in a graph of thousands of
nodes, assemble enough context for the LLM to answer accurately, and
stream the response in real time.  This chapter explains the hybrid
retrieval pipeline that makes this possible.


% ─────────────────────────────────────────────────────────────────────
\section{Hybrid Search}
\label{sec:hybrid-search}

\sysname{} runs two search methods in parallel and fuses their results:

\begin{enumerate}
    \item \textbf{Fulltext search} uses Neo4j's built-in Lucene indexes.
          Two indexes cover 6 fields:
          \begin{itemize}
              \item \ic{decision\_fulltext} --- indexes
                    \ic{trigger}, \ic{context}, \ic{decision},
                    \ic{rationale}, \ic{agent\_decision}, and
                    \ic{agent\_rationale} on \ic{DecisionTrace} nodes.
              \item \ic{entity\_fulltext} --- indexes \ic{name} on
                    \ic{Entity} nodes.
          \end{itemize}
          Fulltext search is fast, deterministic, and handles exact
          keyword matches well.  It struggles with semantic similarity
          (``database'' does not match ``PostgreSQL'').

    \item \textbf{Vector search} uses NVIDIA NV-EmbedQA (2048-dimensional
          embeddings) stored on Neo4j nodes.  Two vector indexes cover
          decisions and entities:
          \begin{itemize}
              \item \ic{decision\_embedding} --- cosine similarity on
                    \ic{DecisionTrace} embeddings.
              \item \ic{entity\_embedding} --- cosine similarity on
                    \ic{Entity} embeddings.
          \end{itemize}
          Vector search handles paraphrases and semantic relationships
          but can miss exact keywords.
\end{enumerate}

Both searches are user-scoped: fulltext results are filtered by
\ic{user\_id}, and vector results require the node to be connected to
the user's decisions.


% ─────────────────────────────────────────────────────────────────────
\section{Reciprocal Rank Fusion}
\label{sec:rrf}

The two ranked lists are combined using Reciprocal Rank Fusion (RRF),
a simple, parameter-light fusion method from Cormack et al.:

\[
    \text{Score}(d) = \frac{1}{k + \text{rank}_{\text{fulltext}}(d)}
                    + \frac{1}{k + \text{rank}_{\text{vector}}(d)}
\]

where $k = 60$ is a smoothing constant that prevents top-ranked results
from dominating the fused score.  Documents that appear in both lists
receive contributions from both terms; documents that appear in only
one list receive a single term.

\begin{lstlisting}[style=python, caption={RRF implementation from \codefile{services/graph\_rag.py}.}]
RRF_K = 60

def rrf_fuse(
    fulltext_ids: list[str],
    vector_ids: list[str],
    k: int = RRF_K,
) -> list[str]:
    scores: dict[str, float] = {}
    for rank, doc_id in enumerate(fulltext_ids, start=1):
        scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    for rank, doc_id in enumerate(vector_ids, start=1):
        scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=lambda d: scores[d], reverse=True)
\end{lstlisting}

RRF was chosen over learned fusion (e.g., a cross-encoder reranker)
because it requires no training data, adds negligible latency, and
performs well when both retrievers are reasonably accurate.

The five steps in detail:

\begin{enumerate}
    \item \textbf{Hybrid retrieval}: Fulltext and vector searches run
          concurrently (on separate Neo4j sessions, since
          \ic{AsyncSession} is not safe for concurrent use).  Results
          are fused with RRF.

    \item \textbf{Top-K seed selection}: The top 5 fused IDs become
          seed nodes for graph expansion.  The default of 5 balances
          context richness against token budget.

    \item \textbf{K-hop expansion}: Starting from seed nodes, APOC's
          \ic{apoc.path.subgraphAll} traverses up to 2 hops outward,
          collecting related decisions and entities.  The result is
          capped at \ic{MAX\_CONTEXT\_NODES = 50} to prevent context
          explosion.

    \item \textbf{Serialization}: The subgraph (nodes + edges) is
          converted to structured Markdown text: decisions with their
          trigger, rationale, and context; entities grouped by type;
          and relationships as labeled edges.

    \item \textbf{LLM generation}: The serialized context is injected
          into the LLM prompt.  The response is streamed as SSE events
          (see Chapter~\ref{ch:backend-api}, Section~\ref{sec:sse-streaming}).
\end{enumerate}

\section{Implementation Details}
\label{sec:graphrag-impl}

The pipeline lives in \codefile{services/graph\_rag.py} as the
\ic{GraphRAGService} class.

\begin{itemize}
    \item \textbf{Constructor}: \ic{GraphRAGService()} takes no arguments.
          The embedding service is initialized internally.  Neo4j sessions
          are passed as keyword arguments to individual methods.

    \item \textbf{Entry point}: \ic{retrieve\_context()} is the main
          method, returning a 3-tuple:
          \begin{lstlisting}[style=python, numbers=none]
async def retrieve_context(
    self, query: str, user_id: str,
    top_k: int = 5, depth: int = 2, session=None,
) -> tuple[dict, str, list[str]]:
    # Returns (subgraph_dict, context_string, seed_ids)
          \end{lstlisting}

    \item \textbf{Fallback}: If vector search fails (embedding service
          down, model timeout), the pipeline falls back to
          fulltext-only retrieval.  The \ic{rrf\_fuse} function handles
          an empty vector list gracefully---fulltext ranks pass through
          unchanged.

    \item \textbf{Singleton}: The service is instantiated once via
          \ic{get\_graph\_rag\_service()} and reused across requests.
\end{itemize}

\section{Ablation}
\label{sec:graphrag-ablation}

Table~\ref{tab:graphrag-ablation} shows how each component contributes
to retrieval quality.  ``Recall'' measures what fraction of relevant
decisions appear in the top-5 results.

\begin{table}[ht]
\centering
\caption{GraphRAG retrieval ablation.  Removing fulltext search causes
the largest quality drop.}
\label{tab:graphrag-ablation}
\begin{tabular}{lcc}
\toprule
\textbf{Configuration} & \textbf{Recall@5} & \textbf{Latency Impact} \\
\midrule
Full pipeline (fulltext + vector + cache) & 100\% & baseline \\
No fulltext (vector only)                 & 13.3\% & --- \\
No vector (fulltext only)                 & 86.7\% & --- \\
No cache                                  & 100\% & 4$\times$ slower \\
No K-hop expansion (seeds only)           & 60\% & 2$\times$ faster \\
\bottomrule
\end{tabular}
\end{table}

\begin{keyinsight}
Fulltext search is the backbone.  Without it, the system misses 87\% of
relevant results.  Vector search contributes the remaining 13\% by finding
semantically related decisions that do not share keywords with the query.
The two methods are complementary, not redundant.
\end{keyinsight}
